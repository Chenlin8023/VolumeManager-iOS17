# 03 · 净化模块为什么一声不响

这篇记录一次真实的排查过程：模块装上了、文件明明在、设置面板毫无变化、
连一行日志都没有。最后查出两个独立的原因，都和代码逻辑无关。

整个过程没有改动一行业务代码，问题全在**打包**和**注入环境**上。
如果你也遇到「插件装上但完全没反应、日志也没有」，可以直接对照本文第 3、4 节。

---

## 1. 现象

- `VolManPrefsClean.dylib` 与 `.plist` 确认躺在
  `/var/jb/Library/MobileSubstrate/DynamicLibraries/` 里
- 设置 → VolumeManager 面板和原版一模一样，打赏、GitHub、Sileo 一样不少
- 模块唯一的日志文件 `vm-prefsclean.log` 从来没被创建过
- 系统没有崩溃、没有进安全模式、没有任何报错

一个**会被加载**的 tweak，`%ctor` 一定会执行，也就一定会留下痕迹。
**完全零痕迹，只能说明它从没被加载过。**

这条推论把排查范围从「注入范围 / 过滤器 / 挂钩点 / 文案匹配」全部排除，
直接指向「文件本身有没有被加载」。

---

## 2. 原因一：dylib 少了执行位（决定性）

解包对比同一目录下的文件权限：

```text
-rwxr-xr-x  VolManAudioQueue.dylib    ← 音量引擎，一直工作正常
-rw-r--r--  VolManPrefsClean.dylib    ← 净化模块，644
```

两者放在同一个目录、用同一种过滤器、由同一个加载器处理，唯一差别就是权限位。

打包脚本里做权限收敛时写的是「统一 644」，把 dylib 一起扫了进去：

```bash
# 错的写法：dylib 也被设成 644
chmod 644 "$OUT/VolManPrefsClean.dylib" "$OUT/VolManPrefsClean.plist"
```

正确写法是分开：

```bash
chmod 755 "$OUT/VolManPrefsClean.dylib"   # 必须带执行位
chmod 644 "$OUT/VolManPrefsClean.plist"
```

### 为什么这个坑特别难查

- `dpkg-deb` 打包**保留源文件权限位**，不会报警
- `make package` 全绿，`dm.pl` 只报「打了个包」，不校验权限
- 装到手机上，包管理器认为安装成功
- 加载器遇到这种文件**不报错、不崩溃，直接跳过**

四个环节没有一处会说「有问题」。所以必须靠构建期断言兜住：

```bash
for d in $(find "$tmp" -name '*.dylib'); do
    if [ ! -x "$d" ]; then
        echo "[权限错误] $n 没有执行位，模块不会被加载"
        VERFAIL=1
    fi
done
```

---

## 3. 原因二：白名单里没有「设置」

修完权限后日志出现了，但内容是这样的：

```text
注入 pid=3995 进程=irisin  bundle=wiki.qaq.irisin          目标=否
注入 pid=4013 进程=Filza   bundle=com.tigisoftware.Filza   目标=否
注入 pid=4089 进程=Sileo   bundle=org.coolstar.SileoStore  目标=否
```

第三方 App 全都有，**唯独没有 `Preferences`**。

RootHide 系越狱默认**不向任何 App 注入**，要按 App 逐个开启白名单
（Bootstrap 的 App List / AppEnabler，或设置里的 Tweak Injection）。
没有勾选的 App，进程里根本不会出现你的 dylib。

对「修改设置面板」这类插件，这意味着：**必须把「设置」本身加进白名单**，
否则模块永远进不去。

### 但也不一定加得进去

在本机实测中，即使把「设置」的开关打开、repsring、反复重启设置进程，
`Preferences` 依旧 0 次注入 —— 而同期所有第三方 App 和 Widget 扩展都正常。
所以可以判定：该环境对 `/Applications` 下系统 App 的注入存在额外的硬性限制。

**结论：在按白名单注入的 RootHide 环境里，不要假设「hook 设置面板」的方案一定能跑通。**
要么改用静态方案（直接改面板二进制），要么接受这个限制。

---

## 4. 一份可直接复用的排查清单

遇到「tweak 装上了但完全没反应」，按顺序查：

| 顺序 | 检查项 | 命令 / 方法 | 判定 |
|---|---|---|---|
| 1 | dylib 有执行位吗 | Filza 看权限，或 `ls -l` | 必须是 `-rwxr-xr-x` |
| 2 | 文件真的在目标目录吗 | Filza 进 `DynamicLibraries` | 与 plist 同目录 |
| 3 | plist 的过滤器写对了吗 | `cat xxx.plist` | `Bundles` 里有没有目标 bundleId |
| 4 | 目标进程被注入了吗 | `%ctor` 里打印 `pid / 进程名 / bundleId` | 有记录 = 加载成功 |
| 5 | 注入环境允许吗 | 越狱工具的白名单 | 白名单类环境必须逐个开启 |
| 6 | 日志路径可写吗 | 主日志 + `/tmp` 双写 | 任一份可见即可 |

第 4 步最关键：**在 `%ctor` 里记一行 pid 和进程名**。
只要这行出现，就说明加载链路是通的，问题在后面；这行不出现，
就说明根本没加载，别再去改业务代码。

---

## 5. 教训小结

1. **「零日志」永远比「报错」信息量大**。先证明模块有没有被加载，再谈逻辑。
2. **dylib 权限必须是 755**，任何「统一 644」的批量收敛都要排除 dylib。
3. 构建脚本的价值不在于能打出包，而在于**能在打错包的时候拒绝交付**。
4. 排查注入型插件时，**先问宿主环境允不允许注入**，再怀疑代码。
   白名单模式下一步之差，就能让人在代码里找一整天的 bug。

## 6. 后续（v1.1.0）：既然注入不可靠，就把净化做进二进制

上面第 3 节已经证明：在按白名单注入的 RootHide 环境里，`com.apple.Preferences`
可能压根收不到注入。既然「运行时摘条目」这条路天生有失败面，v1.1.0 改成**双保险**：

- **静态层**：打包时用 `tools/redact_prefs.py` 把原版面板二进制
  `VolumeManagerPrefs` 里的推广文案 / 收款链接 / GitHub / Sileo 地址 /
  攻击长文按**字节等长**清空，再用 `ldid -S` 重新签名。
  长度不变 → Swift 的字面量长度常量仍成立；NUL 保留 → 仍是合法 C 字符串；
- **运行层**：仍然保留，并把挂钩点从「只挂 `-specifiers`」扩展到
  `-setSpecifiers:` / `-specifiers` / `-buttonEvent:` /
  `UIApplication -openURL:options:completionHandler:`，漏网的按钮也点不下去。

这样即使注入完全失败，面板里的内容也已经不存在了。

**实测结果（iPhone 15 Pro / iOS 17.2.1 / RootHide）**：面板中打赏、GitHub、Sileo、
反盗版条目与末尾长文全部消失，功能开关一个不少，`VolManPrefsCleanStatus` 也能正常写入。
