# 杂音根因分析与修复

- **设备环境**：iPhone 15 Pro / iOS 17.2.1 / Rootless 越狱
- **现象**：抖音个别视频与直播出现强烈杂音，切到下一个视频恢复正常；直播复现率明显更高
- **结论**：根因已通过反汇编定位到 `VolumeManagerAudioQueue.dylib` 的自定义音频渲染回调

---

## 一、插件架构

原版插件由 4 个模块组成，职责清晰：

| 模块 | 语言 | 职责 |
|---|---|---|
| `VolumeManagerAudioQueue.dylib` | Objective-C / C | **每 App 音量的唯一实现者**，读取 `volumeInfo.plist` |
| `VolumeManager.dylib` | Swift + Orion | 只管播放类别与混音（`AVAudioSessionCategoryPlayback` / `isEnabledMixable`） |
| `VolumeManagerSBHUD.dylib` | Swift + Orion | 音量 HUD 窗口 |
| `VolumeManagerPrefs.bundle` | Swift | 设置面板（写配置） |

> 关键判断：出杂音的模块**不含任何 Swift**，`__TEXT.__text` 仅 4,940 字节（约 1,200 条指令）。
> 所以这项工作**不需要 macOS**，WSL2 + Linux 版 Theos 就够了。
> 另外三个 Swift 模块可以当成黑盒原样保留 —— 风险和工作量都压到最低。

配置结构（已确认）：

```
volumeInfo.plist = { "<bundleId>" : { "volume": <float 0..1>, "appName": "<中文名>" }, ... }
```

## 二、根因

### 2.1 插件替换了 App 的音频渲染回调

`VolumeManagerAudioQueue.dylib` 挂了 **4 个 C 函数钩子 + 6 个 ObjC 方法钩子**：

| 类型 | 被挂钩对象 |
|---|---|
| C 函数 ×4 | `AudioUnitSetProperty`、`AudioQueueSetParameter`、`AudioQueuePrime`、`AudioQueueStart` |
| 方法 ×6 | `AVPlayer.play`、`AVPlayer.setVolume:`、`AVAudioPlayer.play`、`AVAudioPlayer.setVolume:`、`AVSampleBufferAudioRenderer.init`、`AVSampleBufferAudioRenderer.setVolume:` |

其中 `AudioUnitSetProperty` 的钩子（`0x6d0c`）逻辑如下：

```asm
0x6d48: ldrb w8, [x8, #0xc0]     ; 读功能总开关
0x6d4c: cbz  w8, orig            ; 开关关闭则放行
0x6d50: cmp  w24, #0x17          ; inID == 23 ?
0x6d54: b.ne orig                ;   23 = kAudioUnitProperty_SetRenderCallback
0x6d58: cmp  w23, #1             ; inScope == 1 (input) ?
0x6d5c: b.ne orig
0x6d60: ldr  x27, [x22, #8]      ; 保存原始 inputProcRefCon
0x6db8: bl   setObject:forKeyedSubscript:   ; 记录 原始inputProc → BundleID 映射
0x6dcc: adr  x8, #0x760c         ; ★ 自己的渲染回调
0x6dd4: stp  x8, x27, [sp, #0x10]; 构造新的 AURenderCallbackStruct
0x6df8: blr  x8                  ; ★ 用「自己的回调」调用原始 AudioUnitSetProperty
```

**即：App 设置的音频渲染回调被悄悄换成了 `0x760c`。**

### 2.2 主因：渲染回调无条件按 Float32 处理 PCM，未检查流格式

替换回调 `0x760c` 的核心循环：

```asm
0x76e0: ldr  w8,  [x19]           ; w8  = ioData->mNumberBuffers
0x76f8: add  x13, x19, x9, lsl #4 ; x13 = &ioData->mBuffers[i]
0x76fc: ldr  w11, [x13, #0xc]     ; w11 = mDataByteSize
0x7708: ldr  x13, [x13, #0x10]    ; x13 = mData 指针
0x770c: ldr  s2,  [x13, x12]      ; ★ 按 32 位 float 读取
0x7710: fcvt d2, s2               ;   转 double
0x7714: fmul d2, d0, d2           ; ★ 乘以该 App 的增益
0x7718: fminnm d2, d2, d1         ;   钳上界（d1 = 2147483647.0）
0x7720: fmax  d2, d2, d3          ;   钳下界（d3 = -2147483648.0）
0x7724: fcvt s2, d2
0x7728: str  s2, [x13, x12]       ;   写回
0x772c: add  x12, x12, #4         ; ★ 步长固定 4 字节
0x7730: cmp  x12, w11
0x7734: b.lo #0x770c
```

两个致命事实：

1. **步长硬编码 4 字节、按 IEEE float 读写** —— 全程没有任何对流格式的判断
   （未读 `mFormatFlags`、未区分 `kAudioFormatFlagIsFloat` / `kAudioFormatFlagIsSignedInteger`、未区分 16/32 位）。
2. **钳位常量是 `2147483647.0` / `-2147483648.0`（INT32 满量程），不是 ±1.0**，
   说明作者假定数据是「用 Float32 容器承载的 32 位定点样本」。

由此推导出的行为：

| 音频流实际格式 | 后果 |
|---|---|
| Float32（值域 ±1.0） | 乘法正确 → **正常**；但钳位无效（阈值 ±2^31 远大于 1.0） |
| SInt32 定点（存于 Float32） | 乘法与钳位均正确 → **正常** |
| **SInt16（每样本 2 字节）** | 每 4 字节被当作一个 float，**两个 int16 样本被整体 reinterpret 成浮点垃圾**，乘增益后写回 → **原始 PCM 被彻底破坏 → 强烈杂音** |

这精确解释了现象：

- 「个别视频有杂音，下一个又正常」→ 不同视频/直播流的 PCM 格式不同，只有命中 16 位整数格式时才爆音；
- 「直播中明显多复现」→ 直播为省带宽普遍采用 16 位 / 较低采样率格式，命中概率远高于点播视频。

### 2.3 次因：实时音频线程内执行 Objective-C 查表

每次渲染回调都会：

```asm
0x76cc: bl 0x7488   → 查 NSMutableDictionary，取该 App 的 NSNumber 音量
0x76dc: bl 0x6a50   → NSNumber → double 转换
```

这两步涉及多次 `objc_msgSend` / `objc_retainAutoreleasedReturnValue` / `objc_release`。
渲染回调运行在**有硬实时 deadline 的音频线程**（通常每 5–10 ms 一次），在其中做 ObjC 消息派发
与字典查找会引入抖动，缓冲区越小越明显 —— 这也是低延迟直播场景更容易出问题、
以及可能出现「咔哒」爆音的原因。

## 三、修复方案

保留同一条路径（`AudioUnitSetProperty(SetRenderCallback)` 是唯一通用的每 App 音量实现方式），
但把回调改成**格式感知**的：

```
渲染回调被调用
   │
   ├─ 查 AudioStreamBasicDescription（缓存，避免每次查询）
   │
   ├─ kAudioFormatFlagIsFloat
   │     ├─ 32 位 → 按 Float32 逐样本缩放，钳位 ±1.0
   │     └─ 64 位 → 按 Float64 逐样本缩放，钳位 ±1.0
   │
   ├─ kAudioFormatFlagIsSignedInteger
   │     ├─ 16 位 → 按 SInt16 缩放，带饱和保护
   │     ├─ 32 位 → 按 SInt32 缩放，带饱和保护
   │     └─  8 位 → 按 SInt8 缩放，带饱和保护
   │
   └─ 其他 / 取不到格式
         └─ 原样放行，一个字节都不动
```

配套的三条约束：

1. **实时线程内零 Objective-C 调用、零内存分配、零日志、零锁** —— 增益值提前缓存在 C 变量里；
2. **宁可不出声，也绝不制造杂音** —— 任何不确定的情况（格式取不到、格式不认识、位数不支持）
   一律放行原始数据；
3. **防二次缩放** —— 渲染回调一旦布防成功，备用层（AVPlayer / AVAudioPlayer /
   AVSampleBufferAudioRenderer 的基准音量回写）立刻让位，避免增益被乘两次。

另外两个一起修掉的缺陷：

| 缺陷 | 根因 | 修法 |
|---|---|---|
| 音量调了没反应 | Rootless 真实目录是 `/var/jb/var/mobile/Library/...`，原模块用裸路径，靠越狱运行时映射才碰巧能用 | 多路径探测 + 正确绕开 libroot 对 `stat()` 参数的就地改写 |
| 改完要重开 App | 原模块监听**两个** Darwin 通知，只监听一个会漏掉从 HUD 调音的路径 | 监听全部 3 个通知 + 0.5 秒文件时间戳轮询兜底 |

## 四、修复后实测结果

在 iPhone 15 Pro / iOS 17.2.1 上逐项确认：

- [x] 不进安全模式（arm64 单切片）
- [x] 无杂音（抖音视频与直播均正常）
- [x] 多个 App 同时播放正常
- [x] 每个 App 的音量单独生效
- [x] 调整后即时刷新，不需要重开 App
